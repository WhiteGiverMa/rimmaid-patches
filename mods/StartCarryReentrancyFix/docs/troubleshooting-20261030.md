# 取料回调污染后续搬运任务：取证记录

## 症状时间线

RimWorld 1.7.4990 下，工作台搬开物品任务在 toil 8 寻路报 NRE。首次静态检查只能证明异常时目的地 B 无效，无法识别写入者；未因 RimIOT 仅标 1.6 就制作 fork。

临时诊断捕获到了完整转换：任务创建时 B 是有效格，工作台来源为 `UFLI_stove`；开始去取肉时仍有效；同 tick 的 `set_B` 由原版 `StartCarryThing` 回调请求无效目标，十余 tick 后搬开任务持此 B 寻路失败。诊断没有改变结果或吞异常。

## 根因与证据

- 当前 `Toils_Haul.StartCarryThing` 先缓存 `curJob`，调用 `TryStartCarry`；0 返回后结束当前任务，却继续操作缓存引用。
- `EndCurrentJob` 可同步寻找新任务；JobMaker 清理后把对象放回池，再创建的任务可以得到同引用、不同 loadID 的对象。
- 旧烹饪回调的参数是 `TargetIndex.B`（原料），新搬开任务的 B 是目的地。继续执行 `SetTarget(B, CarriedThing)`，手中物品为空时便清空了新目的地。
- 独立真实回调红检在模拟取料失败/同步换任务的边界下，使用真实 JobMaker 池复用精确重现了这个写入与错误记录递增；补丁绿检保留新任务 B/count/queues，不多结束新任务。

最初取料为何返回 0 仍未被直接采样；因此结论为已锁定并修复的**后续任务污染路径**，不是 RimIOT/联合灶台的全局兼容性判决。另有模组在 TryStartCarry 内重入换任务也由同一所有权检查覆盖。

## 最终流程

唯一编译回调 → 取料调用前捕获 loadID/Driver → 调用后确认仍持有原任务 → 失败结束后立即返回 → 正常完整/部分取料执行原逻辑。没有全局 NRE catch、目标重选或数量补偿。

## 验证边界

真实 1.7 DLL/Harmony 3 注册和 callback 执行；真实对象池；16 个正常行为组合；异常 identity 与 IL 漂移拒绝。CanCarry、取料返回值、同步任务调度、预约和 records 的引擎边界为 fixture。未自动启动游戏、读取存档或接入运行中的游戏，游戏浅测由正常灶台工作完成一次确认。
